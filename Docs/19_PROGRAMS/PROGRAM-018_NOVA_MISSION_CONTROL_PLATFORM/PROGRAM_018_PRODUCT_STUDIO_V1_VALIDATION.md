## 4. VEEDDA Validation

### 4.1 Employee / beneficiary

- Starts with a recognizable benefit, activity or request outcome.
- Uses Guided mode and mobile-first single-column layouts.
- Sees status, next step, requested information and human support.
- Does not encounter Program, PDS, Gate, Baseline or Capability vocabulary.

Result: PASS.

### 4.2 CSE representative

- Receives decision packages with affected beneficiaries, budget, options, dissent and sources.
- Retains explicit human voting/approval authority.
- Can export a traceable decision receipt and professional deliverable.

Result: PASS.

### 4.3 HR

- Sensitive information is previewed before sharing.
- Role/access boundaries remain visible in relevant expert views.
- AI contributions never become personnel decisions automatically.

Result: PASS.

### 4.4 VEEDDA administrator

- Attention queues and filters support operational volume.
- Bulk behavior is deferred unless confirmation, reversibility and audit are designed.
- Permission denial does not reveal protected data.

Result: PASS FOR V1; bulk operations remain outside certified V1 screen scope.

### 4.5 VEEDDA veto decision

No V1 pattern was found to degrade the certified VEEDDA usage model. Veto NOT EXERCISED.

## 7. Technical Readiness

### 7.1 React mapping boundary

No React code has been created. The package is ready to map into:

- AppShell and route layouts;
- feature routes for Home, Work, Decisions and Deliverables;
- reusable primitive, composite and pattern component layers;
- typed domain view models for work, decision, source, contribution and deliverable;
- state machines for objective creation, AI work, decision and export;
- permission-aware action guards;
- responsive CSS token implementation;
- semantic accessibility contracts;
- API adapters isolated from presentation.

### 7.2 Required implementation contracts

| Contract | Minimum behavior before UI implementation |
| --- | --- |
| Identity and role | current principal, organization, role, permission and locale |
| Work | list/detail, lifecycle, owner, health, next action and change events |
| Plan | phases, actions, dependencies, owners and impact preview |
| Conversation | message stream, tool/action status, cancellation, provenance and retry |
| Source | file/link/data metadata, access, freshness and claim usage |
| Decision | package version, authority, options, consequences, rationale and immutable receipt |
| Expert contribution | actor type, requested scope, result, sources, confidence and acceptance |
| Deliverable | format, audience, sections, review state, version and export status |
| Notification | reason, target deep link, severity, read state and preference |
| Audit | actor, action, target, scope and timestamp for governed actions |

### 7.3 State ownership

- Server state: canonical work, decisions, sources, permissions, audit and deliverables.
- URL state: destination, selected work/tab, filters worth sharing.
- Local durable draft: objective and unsent edits, encrypted/policy-bound as required.
- Ephemeral UI state: open overlay, focus origin and transient selection.
- AI streaming state: cancellable, resumable where supported, never treated as canonical until persisted.

### 7.4 Performance budgets for implementation planning

- Immediate input acknowledgement: under 100 ms perceived.
- Route/shell feedback: under 200 ms.
- Loading explanation: after 2 seconds.
- Background option/retry: after 10 seconds when feasible.
- Core mobile screen target: avoid unnecessary client bundle; measure before setting final numeric budget.
- Long lists: pagination or virtualization without breaking screen-reader access.

### 7.5 Readiness decision

Component and state boundaries are implementable. Actual API and security contract verification is mandatory before React development. Result: READY FOR HANDOFF, NOT AUTHORIZED TO IMPLEMENT.
