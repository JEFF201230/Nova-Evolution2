## Règles des Context Providers

- un Provider ne possède aucune logique métier ;
- un Provider ne modifie jamais une source ;
- un Provider lit uniquement les sources officielles ;
- un Provider ne produit aucune décision ;
- le Context Engine assemble les réponses des Providers ;
- aucun Provider ne remplace le Knowledge Runtime ;
- aucun Provider ne remplace le Knowledge Index.

## Regles officielles de determination du contexte actif

Les regles suivantes definissent l'ordre officiel de determination du chantier actif, du PROGRAM actif, de l'EPIC actif, du LOT actif et des documents faisant autorite. Elles ne creent aucune nouvelle autorite documentaire et ne remplacent aucun registre existant.

### Determination du LOT actif

Le LOT actif est determine en priorite, car il borne l'execution et conditionne tous les autres rattachements de contexte.

Ordre officiel de determination :

1. utiliser le lot explicitement designe par la mission courante lorsque son identifiant respecte le format COS-XXX ;
2. verifier l'existence du fichier `02_PROJECT_MANAGEMENT/COS-XXX.md` correspondant ;
3. verifier que le lot est reference dans `02_PROJECT_MANAGEMENT/LOT_REGISTER.md` lorsque ce registre est disponible ;
4. extraire depuis le lot courant son titre, son objectif, son perimetre autorise, son perimetre interdit, ses livrables, ses criteres d'acceptation et ses criteres de rejet ;
5. si plusieurs lots sont candidats, retenir uniquement le lot explicitement designe par la mission courante et signaler les autres comme contexte adjacent ;
6. si aucun lot n'est designe ou si le fichier du lot est absent, produire une alerte bloquante et demander clarification.

Regle de non-supposition :

- aucun LOT actif ne peut etre deduit uniquement d'un nom de branche Git, d'un fichier modifie, d'un commit recent ou d'une conversation precedente.

### Determination du PROGRAM actif

Le PROGRAM actif est determine a partir du rattachement documentaire du LOT actif.

Ordre officiel de determination :

1. rechercher le LOT actif dans `02_PROJECT_MANAGEMENT/LOT_REGISTER.md` ;
2. utiliser le rattachement PROGRAM declare dans le registre si ce rattachement existe ;
3. a defaut, rechercher le LOT actif dans `02_PROJECT_MANAGEMENT/PROGRAM_REGISTER.md` ;
4. verifier que le PROGRAM identifie possede un identifiant, un nom, un objectif, un statut et une liste de lots associes ;
5. si plusieurs PROGRAM contiennent le meme LOT actif, signaler un conflit de contexte et ne pas choisir arbitrairement ;
6. si aucun PROGRAM n'est rattache au LOT actif, restituer l'absence de PROGRAM actif comme source absente non bloquante, sauf si la mission exige explicitement ce rattachement.

Regle de non-supposition :

- le PROGRAM actif ne peut jamais etre determine par proximite de contenu, par ordre d'apparition dans un registre ou par interpretation de l'objectif du lot.

### Determination de l'EPIC actif

L'EPIC actif est determine uniquement lorsqu'une source documentaire officielle le relie au LOT actif ou au PROGRAM actif.

Ordre officiel de determination :

1. consulter le registre EPIC officiel si ce registre existe dans l'emplacement reserve par le Knowledge Index Storage ;
2. rechercher un rattachement explicite entre l'EPIC et le LOT actif ;
3. a defaut, rechercher un rattachement explicite entre l'EPIC et le PROGRAM actif ;
4. verifier que l'EPIC identifie possede au minimum un identifiant, un objectif ou une description, un statut et une source ;
5. si aucun registre EPIC actif n'existe, restituer `EPIC actif non formalise` sans creer d'EPIC implicite ;
6. si plusieurs EPIC sont candidats sans priorite documentaire explicite, signaler un conflit de contexte et demander clarification.

Regle de non-supposition :

- l'EPIC actif ne peut jamais etre cree, nomme ou complete par deduction a partir du LOT actif.

### Determination du chantier actif

Le chantier actif correspond au cadre de travail operationnel rattache a la mission courante et au LOT actif. Il sert a orienter la reprise de contexte, mais ne remplace ni le PROGRAM, ni l'EPIC, ni le LOT.

Ordre officiel de determination :

1. utiliser le chantier explicitement nomme dans la mission courante lorsqu'il existe ;
2. a defaut, utiliser le chantier declare dans le LOT actif si le lot contient cette information ;
3. a defaut, utiliser le rattachement documentaire disponible dans `02_PROJECT_MANAGEMENT/LOT_REGISTER.md` ou `02_PROJECT_MANAGEMENT/PROGRAM_REGISTER.md` ;
4. a defaut, utiliser le domaine documentaire dominant uniquement s'il est explicitement declare par une source officielle ;
5. si aucun chantier n'est documente, restituer `chantier actif non determine` et ajouter une source absente ;
6. si plusieurs chantiers sont possibles, signaler un conflit et ne pas choisir arbitrairement.

Regle de non-supposition :

- le chantier actif ne peut jamais etre deduit uniquement du dossier modifie, du nom de l'agent, du nom de branche Git ou du dernier fichier consulte.

### Identification des documents faisant autorite

Les documents faisant autorite sont les sources qui bornent l'execution, definissent le statut du contexte ou arbitrent les conflits entre sources.

Ordre officiel de priorite :

1. `MASTER_EXECUTION_SPECIFICATION.md` pour les regles permanentes d'execution, d'autorite, de validation et de rejet ;
2. le fichier du LOT actif `02_PROJECT_MANAGEMENT/COS-XXX.md` pour l'objectif, le perimetre, les livrables, les fichiers autorises, les interdictions et les criteres d'acceptation ;
3. `02_PROJECT_MANAGEMENT/LOT_REGISTER.md` pour le rattachement, le statut et les relations entre lots lorsque le registre est disponible ;
4. `02_PROJECT_MANAGEMENT/PROGRAM_REGISTER.md` pour le PROGRAM actif et ses lots associes lorsque le registre est disponible ;
5. le registre EPIC officiel lorsque ce registre existe ;
6. `01_CORE/DEVELOPMENT_ARCHITECTURE.md` pour les principes d'architecture et de compatibilite PROGRAM, EPIC, LOT, Git, Knowledge Runtime et agents ;
7. `05_RULES/KNOWLEDGE_GOVERNANCE.md` pour les regles d'autorite documentaire, de conflit, de validation et de priorite entre sources ;
8. `04_WORKFLOWS/KNOWLEDGE_OPERATIONS_MANUAL.md` pour les procedures d'exploitation documentaire et de cloture ;
9. `03_AGENTS/README.md` et les fiches `03_AGENTS/*_AGENT.md` pour le role, le perimetre et les criteres d'arret des agents.

Regles d'arbitrage :

- une instruction de mission ne peut pas contredire le MASTER_EXECUTION_SPECIFICATION ;
- le LOT actif prime sur les documents generaux pour le perimetre d'execution ;
- les registres priment sur une mention isolee lorsqu'ils definissent explicitement le rattachement officiel ;
- une source absente doit etre signalee, jamais remplacee par une hypothese ;
- un conflit entre sources d'autorite doit etre restitue comme alerte de contexte et ne doit pas etre resolu arbitrairement par le Context Engine.
