## 6.1 Definition du Runtime des registres

Le Runtime des registres est une couche documentaire d'exploitation du CEREBRAU Knowledge System.

Il definit les regles permettant a un agent IA ou a un operateur humain de produire ou mettre a jour les registres officiels a partir des documents existants autorises, sans ressaisie manuelle et sans modification des documents sources par defaut.

Le Runtime :

- lit les documents sources Markdown autorises par la mission courante ;
- lit les registres existants uniquement lorsque la mission courante l'autorise ;
- qualifie les objets documentaires selon les categories officielles du Knowledge Index ;
- extrait les metadonnees necessaires aux registres ;
- conserve le lien entre chaque entree et son document source ;
- distingue les documents actifs, legacy et archives ;
- applique les statuts documentaires reconnus ;
- respecte les emplacements officiels des registres permanents ;
- produit une sortie lisible par un agent IA et un operateur humain ;
- ne modifie pas les documents sources par defaut ;
- ne remplace pas les fondations du Knowledge System ;
- ne definit aucun code applicatif ;
- ne definit aucun script ;
- ne definit aucun format technique executable.

Le Runtime s'appuie sur les couches existantes :

- Knowledge Index Schema pour les categories, champs, relations et statuts ;
- Knowledge Index Engine pour les operations logiques de construction, maintenance, controle et arret ;
- Knowledge Index Storage pour les emplacements officiels des registres ;
- Knowledge Governance pour les droits, autorites, statuts et conflits ;
- Knowledge Operations Manual pour les procedures d'exploitation et de cloture.

## 6.4 Regles de generation automatique

La generation automatique suit les regles suivantes :

1. lire uniquement les sources autorisees par la mission courante ;
2. identifier les objets documentaires par categorie officielle reconnue ;
3. extraire l'identifiant, le titre, le statut, le proprietaire, la version, les dates, les liens et les dependances lorsqu'ils sont presents ;
4. rattacher chaque objet documentaire a un registre cible autorise ;
5. deduire le registre cible uniquement a partir d'une categorie reconnue, d'un emplacement officiel ou d'une instruction explicite ;
6. refuser toute entree dont la categorie est inconnue ;
7. refuser toute entree sans identifiant lorsqu'un identifiant est obligatoire ;
8. conserver les chemins sources exacts ;
9. conserver les statuts actif, legacy et archive ;
10. ne pas creer de relation non documentee ;
11. ne pas inventer de champ manquant ;
12. ne pas inferer un statut sans preuve documentaire ;
13. ne pas utiliser une archive comme reference active par defaut ;
14. ne pas creer ou modifier un registre si la mission courante ne l'autorise pas ;
15. produire une sortie lisible par un agent IA et un operateur humain.

L'ordre logique de generation est :

1. verifier la mission courante ;
2. verifier les fichiers autorises ;
3. identifier les sources ;
4. qualifier les objets documentaires ;
5. confirmer les categories ;
6. extraire les metadonnees ;
7. verifier les identifiants ;
8. rattacher les objets aux registres cibles ;
9. controler les liens et dependances ;
10. signaler les incoherences ;
11. produire ou mettre a jour uniquement les registres autorises par la mission courante ;
12. produire le rapport factuel de generation lorsque la mission l'autorise.

## 6.5 Regles de mise a jour

Un registre est mis a jour uniquement lorsqu'une mission courante l'autorise explicitement.

Lorsqu'elle est autorisee, la mise a jour suit les regles suivantes :

- mettre a jour un registre lorsqu'un document source est cree, modifie, valide, active, passe en legacy ou archive ;
- conserver l'identifiant stable d'une entree existante ;
- ajouter une entree lorsqu'un nouvel objet documentaire apparait ;
- modifier une entree lorsque les metadonnees source changent ;
- marquer une entree comme legacy lorsque son document source devient legacy ;
- marquer une entree comme archive lorsque son document source devient archive ;
- ne jamais supprimer physiquement une entree sans autorisation explicite ;
- conserver les liens vers les versions ou documents historiques lorsque disponibles ;
- conserver les relations non impactees ;
- signaler les liens casses, ambigus ou inexistants ;
- signaler les dependances manquantes ;
- signaler tout besoin de modification hors perimetre.

Une modification documentaire ne cree pas de nouvel identifiant lorsque l'objet documentaire reste le meme.

Un nouvel identifiant est autorise uniquement lorsqu'un nouvel objet documentaire distinct apparait et que la mission courante autorise son enregistrement.

## 6.6 Regles de synchronisation

La synchronisation des registres respecte l'ordre suivant :

1. synchroniser PROGRAM_REGISTER.md avant EPIC_REGISTER.md ;
2. synchroniser EPIC_REGISTER.md avant LOT_REGISTER.md ;
3. synchroniser DECISION_REGISTER.md avant les registres impactes par les decisions ;
4. synchroniser ARCHITECTURE_REGISTER.md avec REFERENCE_REGISTER.md lorsque les references d'architecture changent ;
5. synchroniser AGENT_REGISTER.md avec WORKFLOW_REGISTER.md lorsque les workflows attribuent un role a un agent ;
6. synchroniser RULE_REGISTER.md avec KNOWLEDGE_GOVERNANCE.md et les documents de regles autorises ;
7. synchroniser ARCHIVE_REGISTER.md apres tout passage en Archive.

La synchronisation doit :

- conserver les identifiants stables ;
- conserver les chemins sources ;
- conserver les relations explicites ;
- respecter les statuts documentaires ;
- signaler toute dependance manquante avant production finale ;
- signaler tout conflit entre deux documents actifs ;
- signaler toute decision incompatible non resolue.

Une synchronisation ne doit pas :

- modifier les documents sources par defaut ;
- creer un registre hors mission ;
- modifier un registre non autorise ;
- fusionner deux versions concurrentes sans mission explicite ;
- rendre prioritaire un document legacy ou archive par defaut.

## 6.7 Regles de validation

Chaque registre produit ou mis a jour par une mission future devra respecter les regles suivantes :

- le registre respecte son nom officiel ;
- le registre respecte son emplacement officiel ;
- chaque entree possede un identifiant ou une cle de rattachement ;
- chaque entree pointe vers au moins un document source ;
- chaque entree possede un type reconnu ;
- chaque entree possede un statut reconnu ;
- les doublons d'identifiants sont interdits ;
- les chemins inexistants sont signales ;
- les relations parent-enfant sont coherentes ;
- les documents archives ne sont pas presentes comme actifs ;
- les documents legacy sont signales comme legacy ;
- les dependances sont explicites ;
- les relations non documentees sont interdites ;
- les champs manquants ne sont pas inventes ;
- les entrees incompletes sont signalees selon les regles du lot applicable.

Un registre est conforme uniquement si aucune entree active ne viole les controles d'identifiant, de categorie, de statut, de chemin source, de dependance et de cycle de vie.

En cas d'arret, le Runtime produit uniquement un signalement factuel compatible avec les regles du lot en cours.
